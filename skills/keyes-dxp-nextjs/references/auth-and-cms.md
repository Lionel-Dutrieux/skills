# Auth and CMS

## Which auth?

```
Does the app use PayloadCMS?
├── yes → use Payload's built-in auth. Do NOT install Better Auth.
└── no  → Better Auth.
```

Never next-auth / Auth.js, never Clerk. Running two auth systems side by side is a bug, not
an architecture.

## Better Auth

```ts
// lib/auth.ts
import { betterAuth } from "better-auth"
import { drizzleAdapter } from "better-auth/adapters/drizzle"
import { db } from "@/db"
import { env } from "@/env"

export const auth = betterAuth({
  database: drizzleAdapter(db, { provider: "pg" }),
  emailAndPassword: { enabled: true },
  socialProviders: {
    // ids/secrets come from `env`, never process.env directly
  },
})
```

```ts
// app/api/auth/[...all]/route.ts
import { toNextJsHandler } from "better-auth/next-js"
import { auth } from "@/lib/auth"

export const { GET, POST } = toNextJsHandler(auth)
```

```ts
// lib/auth-client.ts
import { createAuthClient } from "better-auth/react"

export const authClient = createAuthClient()
export const { signIn, signOut, useSession } = authClient
```

Auth tables are generated by the Better Auth CLI and then migrated through Drizzle — they
are part of the same schema as the rest of the app, not a separate database.

## Reading the session

Server side (`headers()` is async):

```ts
import { headers } from "next/headers"
import { auth } from "@/lib/auth"

const session = await auth.api.getSession({ headers: await headers() })
```

In server actions this happens inside `authActionClient` — do not re-implement it per
action (see `server-actions.md`). In route handlers, check it explicitly.

Client side, `useSession()` is for **rendering** (showing a name, hiding a menu item).
It is never an authorization check. Every protected read and write re-verifies on the
server.

## Authorization

- Hiding a button is UX. The server decides.
- Permission checks live in middleware (`authActionClient`, `adminActionClient`) or at the
  top of the route handler, plus an ownership check in the query itself
  (`where eq(posts.authorId, ctx.user.id)`).
- Next.js `middleware.ts` is for cheap redirects of unauthenticated traffic only. It runs
  before you know enough to authorize; never treat it as the security boundary.

## PayloadCMS

Payload runs **inside** the Next.js app — same repo, same deployment, admin UI under
`/admin`, no separate backend service.

```ts
// Server Component — Local API, no HTTP round-trip
import config from "@payload-config"
import { getPayload } from "payload"

export default async function PostsPage() {
  const payload = await getPayload({ config })
  const { docs } = await payload.find({
    collection: "posts",
    limit: 10,
    overrideAccess: false,           // enforce access control
    user: await getCurrentUser(),    // ...as this user
  })
  return <PostList posts={docs} />
}
```

Rules:

- Use the **Local API** in Server Components and server actions. Do not HTTP-fetch your own
  Payload REST API from the same process.
- `overrideAccess: false` plus a `user` whenever the request is on behalf of someone.
  Defaulting to `overrideAccess: true` silently bypasses every access control rule you
  wrote.
- Access control belongs in the collection config (`access: { read, create, update, delete }`),
  so it applies to the admin UI, the REST/GraphQL APIs and your own code alike.
- Generated types (`payload-types.ts`) are the source of truth for document shapes —
  import them, never redeclare them.
- Payload's Postgres adapter is Drizzle underneath. Application tables share that setup —
  see `database.md`.
